# 平台公开预览取数

计划书平台对部分产品提供不需要登录的“利益演示预览”：把产品的录入参数发给演示接口，接口返回逐年利益表。本技能只使用这一条路线。

## 先确认三件事

1. **使用人同意。** 每次取数前说明要访问的平台、要取的产品和组合数量、预计请求数，得到同意后再执行。同意人和时间通过 `--consent` 写进请求日志。
2. **使用人提供产品录入配置。** 即平台产品录入页加载的那份产品配置 JSON（内含 `initData.inputData` 和可选的 `verifyData`）。获取这份配置的接口目前需要登录，**本技能不提供获取办法，也不代替使用人登录**；由使用人在自己有权使用的环境里导出后交给你。没有配置就不能走这条路线。
3. **官方资料确实没有。** 平台数据是第三方数据，只用来补官方资料缺的部分。

## 边界

| 做 | 不做 |
|---|---|
| 向公开预览演示接口发送产品参数，读取返回的逐年表 | 登录、注册、使用任何账号 |
| 单线程、低频、失败不重试 | 读取、保存、传递会话、令牌、Cookie |
| 保存原始返回（去掉个人信息字段）和请求日志 | 处理或规避验证码、滑块 |
| 遇到拒绝立即停止并告知使用人 | 调用需要签名的计算/上传接口、生成计划书 |
| | 付费、使用会员权益、界面自动化、更换网络或标识重试 |

停止条件（任一出现即停，写入停止标记，后续调用一律拒绝）：

- 返回内容含登录、会员、验证、频繁、次数用完、生成上限一类提示，或对应的风险代码；
- HTTP 状态不是 200，或返回不是 JSON；
- 网络错误（不自动重试，由使用人决定是否再试）；
- 当日请求数达到上限（默认 200）。

停止标记是状态目录里的 `PLATFORM_STOP.json`。只有使用人可以删除它；Agent 不要删除、改名或换一个状态目录来继续。

## 三步

### 1. 选参数（不联网）

```bash
PB platform-choose --init 产品配置.json --pay 5 --term "保至105周岁；60岁起年领" --out work/p/row123/pbdata.json
```

把底稿组合（交费年数、保险期间文字）映射到平台录入项，并沿平台自己的选项校验树检查该年龄性别下这个组合是否提供。输出 `offered: false` 表示平台不提供这个组合，到此为止。`notes` 里的提示要逐条看：

- `mode=premium`：按保费录入，直接是 10 万元。
- `mode=units` / `amount`：平台按份数或保额录入。先取一次看返回的保费，再用 `--set num=…` 或 `--set baoe=…` 调到年交保费等于 10 万元后重取（先删掉该目录下旧的返回文件）。
- `element extra1 … left at its default`：平台有额外选项（例如领取方式），确认默认值与底稿组合一致，不一致用 `--set` 指定。

### 2. 取数

```bash
PB platform-fetch --pbdata work/p/row123/pbdata.json --out work/p/row123 --state work/p/_state \
                  --consent "张三 2026-01-05 同意本次取数" --tag "row123 5年交" [--annuity]
```

- 默认取两种红利方式：`bonus_acc`（累积生息）、`bonus_add`（交清增额）。年金加 `--annuity`（年金现金领取）。
- 请求体要点：`pbData`（第 1 步的结果）、`bonus=mid`（中档）、`accRate=0.0175`、`singleCalType=2`。请求头只有 Content-Type、User-Agent、Origin/Referer，没有任何身份信息。
- 已存在的返回文件不会重复请求。所有组合共用同一个 `--state` 目录，这样日上限和停止标记才有效。
- 输出目录：`pbdata.json`、`detail_bonus_acc.json`、`detail_bonus_add.json`、`status.json`；状态目录：`platform_requests.jsonl`。
- 退出码 3 = 已停止。把 `reason` 原样告诉使用人。

平台对某个组合没有数据时会返回业务提示（例如“案例数据处理”），这不是拒绝，记为“平台该组合无数据”。

### 3. 核对并转换

```bash
PB platform-convert 工作簿.xlsx --row 123 --dir work/p/row123 --out work/specs/row123.json \
                    --entry "平台条目【编号、名称、平台标注】" --archive "资料库/平台/row123"
```

转换前的核对（任何一项不过，该部分不生成）：

| 核对 | 规则 |
|---|---|
| 保费 | 平台年度保费 = 底稿保费，交费年数一致 |
| 保证现金价值 | 平台现金价值与底稿 E 列逐年一致（差 ≤ 1 元或十万分之一）。这一步证明平台算的是同一产品、同一组合 |
| 年度数 | 平台年度数不少于逐年块年度数减 1 |
| 累积生息 | 有当年红利列；自行按累积利率累积的余额与平台余额相差 < 1 元 |
| 交清增额 | 总现价 = 保证现价 + 红利现价（含终了红利的另行标注）；总现价不低于保证现价；年金能分出红利年金 |

演示利率判定：见 methodology“演示利率的判定”。输出里的 `info.accumulate.verified` 为 `true` 才是“按比值认定”；为 `false` 时生成的标注写“未能认定”，是否照此填列先问使用人。

平台保证现金价值与底稿成固定比例时（平台按另一保额列示），命令会停下并给出系数。需要你判断红利列是否同一口径：

- 红利比值在两种假设下哪个合理（接近期望比值的那个）；
- 有官方披露点时哪种折算能对上。

判断后用 `--scale all`（全部列同比例折算）或 `--scale base`（只有保证现价按另一保额列示，红利列已是实际口径）重跑。判断不了就不填。

## 返回表常见列

| 键 | 含义 |
|---|---|
| `baof` | 年度保费 |
| `cash_value_tmp`、`base_cash_value`、`cash_value1`、`cash_value` | 保证现金价值（不同条目用不同键） |
| `total_cash_value` | 含红利的总现金价值 |
| `bonus`、`bonus1`、`bonus_zs` | 当年红利 |
| `bonus_sum` | 累积红利余额 |
| `annuity_year` | 当年年金 |
| `pua_cash_value`、`bonus_baoe_cv`、`bonus_cash_value` | 红利保额/交清增额的现金价值 |
| `pua_annuity`、`bonus_live_end`、`pua_live_end` | 红利年金 |
| `pua_expire_insurance`、`bonus_expire_insurance` | 红利满期金 |
| `bonus_end` | 终了红利 |
| `pua_baoe_acc` | 累计交清增额保额 |

遇到没见过的列或机制（例如红利按保额而非现价计算、年金现价为给付前口径），不要套用现成转换；把情况报告给使用人。
